# CC Phase 4 Matrix — Document C: Revised / Removed Items, With Rationale

**Scope covered:** Categories 15–21

---

### Category 15 — Dashboard / Home Screen & Visual Hierarchy

- **REVISE** — Original interpretation that Current/Planning/etc. should display their projects directly on the Home Screen. Reason: this was Kurt's own correction mid-session — the Home Screen presents the functions/categories only; the underlying projects are reached one level deeper, after a function button is clicked. Reflected in the revised P4-R221 in Document A.

- **REMOVE** — "Current Focus" as a Home Screen section. Reason: Kurt explicitly stated this information belongs behind project selection, not on the home screen itself ("I'd remove 'Current Focus' from the Dashboard design entirely. That was me putting information on the home screen that you specifically wanted behind the project selection.").

### Category 16 — Home Screen Functions

- **REVISE** — Ideas must not be treated simply as another ordinary project-status folder. Reason: Ideas behaves differently from Current/Planning/Ongoing/Archive — it's a workspace for informal, pre-project material rather than a view over formal Project Records. This distinction is carried forward into Category 17's more detailed treatment.

- **REVISE** — New Project and Archive are different kinds of functions from the project-category buttons. Reason: New Project is a creation mechanism (not a project view), and Archive is access to past projects (not an ordinary status filter) — neither should be conceptually collapsed into "just another status button."

### Category 18 — Project Workspace Editing & Permissions

- **REVISE** — "Kurt can edit..." must be understood architecturally as "Project Owner can edit...". Reason: same correction as Category 13 — the finished CC must not encode Kurt as the universal owner; this is the Project Owner generalization applied consistently to the editing-permissions category.

### Category 20 — Search & Knowledge Retrieval

- **REVISE** — File Search should not be defined as limited to files already "known/associated" with CC. Reason: the original File/Project search model implicitly assumed CC already knew about a file. The corrected model distinguishes File Search (content within the selected search domain) from Disk Search (broader filesystem discovery of files CC doesn't yet know about) — this was prompted directly by Kurt's Safari/Chrome download-location example.

- **Process note (numbering collision, not itself a REVISE/REMOVE item):** IDs P4-R270–278 were assigned twice in the source material — first to the original two-scope (File/Project) search set, then reassigned to the later four-scope (File/Project/Repository/Disk) revision after Kurt's input. Only the final four-scope version is authoritative and is what appears in Document A. This numbering collision will need correcting during formal specification, the same as the Category 3 and Category 4 collisions noted in the Steps 1–7 chunk.
